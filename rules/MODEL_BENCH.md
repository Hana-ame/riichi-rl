# MahjongNet：模型大小 vs 推理响应时间

> 2026-11-04 · CPU-only 实测（WSL2 / Ryzen 5 3600）
> 脚本：`bench/bench_model.py`；原始读数：`bench/results_cpu1.json`、`bench/results_cpu12.json`、`bench/results_threads.json`、`bench/results_gpu.json`
> 未改动任何现有模型/训练代码，只新增 `bench/` 与本文档。

---

## 0. 结论先看

1. **推理侧根本不缺预算。** 测过的最大模型 256ch×6blk（3,581,367 参数）端到端单步决策 **7.24 ms**；现有 `riichi_net.pt`（1,652,967）**4.42 ms**；444K 档 **1.77 ms**。GUI/对局按 0.35 s/步推进，单步只占 0.5%–2%。**在 444K–3.58M 范围内，模型大小不是实时性的约束。**
2. **真正的约束是 CPU 批量吞吐（训练/自对弈）。** batch=200 吞吐从 5,443 samples/s（444K）掉到 329 samples/s（3.58M）：参数 8×，吞吐 16.5× 下降。
3. **同参数量下，浅而宽比深而窄快。** 160ch×4blk（1.32M）单次 1.96 ms / 1,214 samples/s，128ch×8blk（1.40M）单次 3.17 ms / 880 samples/s——参数几乎一样，延迟差 1.6×。串行 block 数是单样本延迟的主因。
4. **选型建议**：质量基线保持 **160ch/6blk（1.65M，现状）**；要提速先减 block（160×4）而不是砍 channels；吞吐优先用 96×6 / 128×6；**不建议上 256ch（>2.7M）**——无质量证据支持（`mahjong/net.py` 调研结论是 bc49 的 2.00M 已够），吞吐却只有 160×6 的 70%（256×4）/ 44%（256×6）。
5. **部署线程数是比模型大小更值得改的一项。** 本机 `cpu_only.py` 默认 12 线程跑 batch=1 反而比 1 线程慢 4× 以上（线程扫描 4–5×；并发负载下均值可差 10–50×），且出现 0.5 s 级长尾（见 §4）。建议：**在线推理 `torch.set_num_threads(1)`（最多 2）；批量训练/自对弈前向用 4–8 线程**。

### 1.2 配置覆盖（11/11 测完）

| 类别 | 配置 | 说明 |
| --- | --- | --- |
| 现有权重 | `ckpt-160x6` | `checkpoints/riichi_net.pt`，strict load 成功，1,652,967 参数，与任务「约 1.65M」一致 |
| 现有权重 | `ckpt-64x4-ckfw` | `ckfw.pt`，strict load 成功，453,232 参数；hh_v1 头（47 动作 / touch_dim=8 / extra_scalar=12） |
| 缺失权重替代 | `64x4` | `checkpoints/ppo_v1.pt` **不存在**（`checkpoints/` 下无 `ppo*`；全仓 `find . -name '*ppo*'` 只命中 `train_ppo.py`、`opponent_model.*`，无 ppo 权重）。按同结构 64ch/4blk/54 动作重建 = **444,791 参数**，正好是任务说的「约 444K」，故用它代表该 size |
| 网格 | 96×4 / 96×6 / 128×6 / 128×8 / 160×4 / 160×8 / 256×4 / 256×6 | 随机初始化（计时与权重无关） |

> 说明：`ckfw.pt` 的输入是 774+8+12=794 维（多出的 20 个标量只进 `head_fc`，对卷积主干无影响），其余配置 774 维。

### 1.3 计时协议

- `model.eval()` + `torch.no_grad()`，先 warmup 再计时；
- 单样本：batch=1，warmup 20 次；batch64：warmup 10 / 每轮 30 次；batch200：warmup 5 / 每轮 20 次；
- 每档重复 **3 轮**，池化 3 轮全部读数后取均值（同时记录 p50/p90/std），以抵消 WSL 主机上 `serve_game` 等并发进程的抖动；
- CPU 单次延迟用 `time.perf_counter()` **逐次**计时；GPU 用整段计时 + `torch.cuda.synchronize()` 后除以次数；
- 端到端 = `ObsEncoder.encode` → 拼 774 向量 → 前向 → 加 `-1e9` 掩码 → `argmax`，直接照 `play_model.py:46-60` 的写法；真 env（seed=12345）里固定一个 pending 玩家反复决策；
- 主表线程数 = **1**。原因：`cpu_only.py` 默认 12 线程在本机 batch=1 下被 OpenMP 同步开销淹没（同权重 1 线程 1.13 ms vs 12 线程均值 15 ms，且长尾到 0.5 s），用默认值测出来的只是线程池行为，不是模型大小效应。`--threads default` 的对照完整保留在 §4。

## 4. 附：线程数的影响（比模型大小更关键）

### 4.1 `--threads default`（cpu_only 的 12 线程）

| 配置 | 参数量 | 单次 mean±std ms | 单次 p50 | 单次 p90 | batch200 ms | 吞吐 samples/s |
|---|---|---|---|---|---|---|
| 64x4 | 444,791 | 15.34 ± 47.65 | 5.68 | 14.35 | 325.5 | 614 |
| 96x6 | 797,447 | 103.83 ± 224.49 | 3.77 | 540.07 | 168.2 | 1,189 |
| ckpt-160x6 | 1,652,967 | 35.09 ± 122.96 | 7.74 | 22.02 | 235.6 | 849 |
| 256x6 | 3,581,367 | 259.51 ± 317.60 | 16.89 | 715.68 | 373.9 | 535 |

12 线程的读数是**双峰**的：p50 有时接近 1 线程，但均值被 0.5–0.7 s 的长尾拉爆，且 batch200 并不比 1 线程快（256x6：373.9 ms vs 608.2 ms 只快 1.6×，远不及 12×）。同一次运行里 96x6 的 p90 甚至到 540 ms。**这不是模型属性，是 OpenMP 自旋等待 + 与 `serve_game` 抢核的结果；不能拿它做选型。**

## 6. 结论与选型建议

### 6.1 多大的模型还能在实时对局里跑？

按「单步决策 ≤ 50 ms 都算实时」的宽松标准和 GUI 的 350 ms 步进：

- **所有测过的配置（444K–3.58M）都能实时**：端到端 1.77–7.24 ms，最坏也只占 GUI 步进的 2%。
- 即使外推到 ~10M 参数，按线性趋势单步 ~15–20 ms，仍在实时区内。**实时性不是选型瓶颈。**
- 真正会在实时对局里咬人的是线程配置错误（§4），不是模型大小。

### 6.2 建议的 size

| 目标 | 推荐 | 依据 |
| --- | --- | --- |
| 质量基线（当前主线） | **160ch / 6blk = 1.65M** | 现有 `riichi_net.pt`；单步 4.42 ms，batch200 752 samples/s；与调研的 bc49 2.00M 同量级 |
| 想给推理/自对弈提速 | **160ch / 4blk = 1.32M** | 单次 1.96 ms（比 128×8 快 1.6×）、1,214 samples/s；仅比 160×6 少 2 个 block |
| 吞吐优先（大批自对弈） | **96ch / 6blk = 0.80M** 或 **128ch / 6blk = 1.18M** | 1,730 / 1,231 samples/s；单次 1.93 / 2.43 ms |
| 不推荐 | 256ch（2.7M / 3.58M） | 无质量证据支持 >2M；batch200 吞吐跌到 527 / 329 samples/s，是 160×6 的 70% / 44%，训练数据生成明显变慢 |
| 想试更大 | 先做 128×8 / 160×8 的 arena 对照，再决定 | 参数 1.4–2.0M，单次 3.2–4.2 ms，吞吐 880 / 581 samples/s；不要直接跳 256 |

### 6.3 一句话

**模型从 444K 涨到 3.58M，单步只从 1.8 ms 涨到 7.2 ms（仍远低于实时线），但 CPU 批量吞吐掉了 16.5×——所以「多大能实时」的答案是很宽裕的，真正该省的是训练/自对弈的算力，以及把默认 12 线程改成推理 1–2 线程、训练 4–8 线程。**
