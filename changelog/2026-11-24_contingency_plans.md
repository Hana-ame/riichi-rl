# 立直麻将 AI（riichi-rl）多套预备技术方案与实施路线图

* **日期**：2026-11-24

* **关联文档**：`changelog/2026-11-24_root_cause_analysis.md`

* **目标**：针对不同算力预算、开发周期和代码改造深度，提供 **4 套可落地的预备方案（Plan A / B / C / D）**，并明确每套方案的改动清单、阶段验收门槛与回退机制。

## 方案总览与选型决策矩阵

| 方案 | 核心思路 | 改动幅度 | 算力需求 | 预期周期 | 能否解决 4 大问题 | 适用场景 | 
| ----- | ----- | ----- | ----- | ----- | ----- | ----- | 
| **方案 A（推荐优先）** | 修复自研引擎致命 Bug + 补全 `obs2` 特征 + **天凤凤桌牌谱 BC**（`DualStreamMahjongNet`） | 中 | 单卡 GPU（或中配多核 CPU） | 2–4 天 | 副露✅ 弃胡✅ 流听✅ 可训练✅ | 最快出「会副露/会弃和/会流听」的可用强模型，直接作为后续 RL 基座 | 
| **方案 B（主线完整 RL）** | 在方案 A 基础上，升级 **GAE-PPO + 半庄顺位分（Uma）+ KL 锚定 + 多进程 Actor-Learner** | 中偏大 | 单卡/多卡 GPU + 多核 CPU | 1–2 周 | 全部✅，且可突破人类模仿上限 | 有 GPU 算力、目标冲击高段位/击败 Suphx 参照 | 
| **方案 C（模块化/混合专家）** | 引擎修复后，采用「主弃牌网络 + 独立副露头 + 独立防守/危险张模块」解耦迭代 + 外部强模型蒸馏 | 中 | 低–中（单卡或 CPU） | 3–5 天 | 副露✅ 弃胡✅ 流听⚠️ | 端到端联合训练暂时难收敛时的稳妥兜底方案，便于单点消融与排障 | 
| **方案 D（高速外部引擎替代）** | 放弃纯 Python `MahjongEnv` 训练循环，切换至 **C++/Rust 高速引擎**（`mjx` / `libriichi` / Mortal 生态）+ 离线/在线 RL | 大 | 中–高（GPU + 多核） | 2–4 周 | 全部✅，彻底解除吞吐瓶颈（100×+ 加速） | 长期投入、需要千万级自对弈局数做真正强 RL | 

> **硬前提（所有方案通用）**：只要还在使用本仓库的 `MahjongEnv` 做训练或评测，**必须先完成「Phase 0 引擎与观测修复」**，否则任何方案在本地评测中都会继续出现副露零和牌与流局错算。

## Phase 0：公共前置修复（所有方案必做，约 0.5–1 天）

### 0.1 引擎规则层彻底止血

1. **废弃自研算分，全面切到 `MahjongRepository/mahjong`（`mahjong/refengine.py` + `mahjong/env.py`）**：

   * 修复 `refengine.py:42` 的 `to136`：按牌种维护已分配计数（同类牌依次分配 `t*4 + 0, +1, +2, +3`，赤五固定映射到 `16(0m)/52(0p)/88(0s)`）。

   * 为 `score_hand` 完整传入 `melds`（转换为上游 `Meld(meld_type, tiles, opened)`）、`dora_indicators`、`player_wind`、`round_wind`、`is_tsumo`、`is_riichi`、`is_ippatsu`、`is_daburu_riichi`、`has_aka_dora=True`、`has_open_tanyao=True`。

   * `env.py` 的 `_best_score`、`_can_tsumo`、`_can_ron` 统一调用修复后的 `refengine.score_hand`，彻底绕过有 Bug 的 `hand.py:enumerate_all_with_melds` 与 `scoring.py:_detect_yakus`（或同步修复 `hand.py` 仅作单元测试兼容）。

2. **修复副露与响应优先级（`mahjong/env.py:890, 701-705`）**：

   * 响应裁决顺序改为：`ACT_RON` > `ACT_PON / ACT_MINKAN` > `ACT_CHI`。

   * 移除响应阶段的 `ACT_ADD_KAN`（加杠仅在自己摸牌的 `DISCARD` 阶段合法）。

   * 移除 `ACT_RYUUKYOKU` / `ACT_NAGASHI` 非标准主动流局动作（或保留开关默认彻底关闭）。

3. **修复流局、王牌与连庄规则（`mahjong/env.py` + `mahjong/hanchan.py`）**：

   * `_draw_tile` 扣除 14 张王牌（`len(self.wall) - 14`，每次杠后王牌取岭上牌并减可摸牌数），统一以「可摸牌山耗尽（剩余 0 张）」作为荒牌流局条件，替代 `turn >= 72` 硬截断。

   * `_finish_ryuukyoku` 罚符严格按总池 3000 分配：1 听（+3000 / -1000）、2 听（+1500 / -1500）、3 听（+1000 / -3000）。

   * `_is_tenpai` 改用暗牌 + 副露组数（不含杠的第 4 张重复计数）判听牌，修掉杠后 14 张误删 Bug。

   * `hanchan.py:96-107`：流局时若 `result.tenpai[self.dealer]` 为真则庄家连庄（`kyoku` 不变、`honba += 1`），否则轮庄 `dealer = (dealer + 1) % 4` 且推进局数；和牌时若 `winner == dealer` 则连庄（`honba += 1`），否则 `dealer = (dealer + 1) % 4`、`honba = 0` 且推进局数。

### 0.2 观测与动作空间补全（`mahjong/obs2.py` + `train_hanchan.py`）

1. **新增关键防守与局势平面（`obs2.py`）**：

   * **3 家对手立直标志**（3 个常量平面或显式标量，按相对座位 1=下家/2=对家/3=上家）。

   * **3 家对手各自现物（安全牌）平面**（3×34 二值平面：该对手牌河全部牌 + 该对手立直后全场所有人打出的牌）。

   * **手牌 4 层二值编码**（`>=1, >=2, >=3, >=4` 共 4 平面，替代单层 `0..4` 计数，卷积和线性层更容易识别对子/刻子）。

   * **赤宝牌平面**（标记自家手牌与场上已见红 5m/5p/5s）。

   * **响应阶段特征**：弃牌者相对座位 one-hot（3 维）+ 候选吃/碰/杠涉及的牌面平面。

   * **准确余牌进度**：`(len(wall) - 14 - wall_idx) / 70.0` + 最后 4 巡倒计时提示，方便模型感知流听窗口。

2. **修正吃牌动作槽（`train_hanchan.py:86-87`）**：

   * 将 `SLOT_CHI_BASE + (action.tile % 3)` 改为按被吃牌在顺子中的**相对位置**映射：`0=左吃(吃最小张, tile==start)`、`1=中吃(嵌张, tile==start+1)`、`2=右吃(吃最大张, tile==start+2)`。

### Phase 0 验收门槛

* 单元测试新增并通过：副露断幺九（含全顺子 30 符）、副露役牌（白/发/中/自风/场风）、副露含宝牌/赤五、碰优先于吃、2 听 2 不听 `±1500`、庄家流局听牌连庄、开杠后听牌判定。

* 4×`RandomLegal` 与 4×`SuphxFullAgent` 各跑 200 局：零异常、牌数守恒 100%、副露和牌占比恢复正常（不再为 0%）。

## 方案 A（首选快速见效）：Phase 0 + 天凤凤桌全量 BC（DualStream 架构）

### 核心逻辑

彻底放弃用 `GreedyTenpai` 生成教师数据——`GreedyTenpai` 既不会副露、也不会弃和、更不懂流听。仓库里已经打通了天凤凤桌牌谱（`houou_data.py`，250 万+ 局高段位人类实战，天然包含高质量的副露速度型打法、面对立直的现物弃和、以及终盘形式听牌）。先用正确特征 + `DualStreamMahjongNet` 吃透凤桌牌谱，一步解决 4 大问题中的 3.5 个。

### 具体实施步骤

1. **统一离线/在线特征对齐**：

   * 写一个统一的特征适配器，将 `houou_data.Decision` 直接编码成与 Phase 0 新版 `obs2 + event_stream` **完全一致**的张量（并用 `test_encode_consistency.py` 逐字段断言在线 `MahjongEnv` 与离线 `houou_data` 编码误差为 0）。

2. **动作空间与样本平衡**：

   * 保留 47 槽统一策略头（34 切牌 + 13 特殊，其中吃槽改为左/中/右相对位置）。

   * 不采用 `train_teacher_bc.py` 那种极端硬权重（`special=20, pass=0.1` 会导致过叫），而是按**真实合法决策点**做轻度平衡或 Focal Loss / 温度校准；对「仅有 PASS 合法」的无意义决策点直接过滤不入训练。

3. **辅助多任务监督（增强弃和与打点意识）**：

   * 复用 `DualStreamMahjongNet.aux_danger_head`，在凤桌数据上加旁路监督（预测对手和牌张/放铳危险张，权重 0.1–0.2），强迫主干学会读牌河与立直防守。

   * 可选增加 Value 头离线回归监督（目标 = 该半庄最终顺位点 + 局内净得分归一化），为后续方案 B 的 PPO 直接提供高质量 Critic 初始化。

4. **训练规模**：

   * 先用 20–50 万决策点（约 1–2 个 shard）在 `DualStreamMahjongNet(d_model=128, n_layers=3)` 验证 pipeline 与指标；确认无特征错位后扩到 500 万–1500 万决策点（`d_model=192~256, n_layers=4~6`），AdamW + Cosine/OneCycleLR。

### 阶段验收指标（4×同模型 & vs 基准池 200+ 局）

* **弃牌 Top-1 准确率（凤桌验证集）**：≥ 68%–75%（高段位人类牌谱标准区间）。

* **副露行为**：叫牌频率 1.5–3.5 次/局，且**副露局和牌率 > 20%**（证明副露带来正收益）。

* **弃和能力**：面对先制立直时，非听牌/低打点手牌切现物率显著高于基线，全对局座位放铳率控制在 **10%–14%**，座位和牌率达到 **18%–24%**。

* **流听能力**：荒牌流局时听牌率 ≥ 35%–45%，终盘（剩余 ≤ 12 巡）可见主动保听或副露抢形式听牌。

### 风险与预案

* **风险**：离线 `houou_data` 与在线 `MahjongEnv` 在细节字段（如立直后通牌、赤五标记、巡目定义）存在分布偏移（Distribution Shift）。

* **预案**：上线前强制跑 1000 步 `encode_consistency` 对齐测试；若在线副露频率偏高/偏低，仅对响应阶段的 `PASS` logit 做单标量温度/偏置校准（不改弃牌头）。

## 方案 B（主线完整 RL）：方案 A 底座 + GAE-PPO 半庄顺位强化学习

### 核心逻辑

解决「从 BC 起步做 RL 稳定退化」的根本病灶：**把高方差单局 MC 回报升级为半庄级 GAE-PPO + 强 KL 锚定 + 真实顺位激励**。

### 具体实施步骤

1. **奖励函数重构（替换 `scenarios.py`）**：

   * **局内净点**：用 `env.net_points(result, start_points)`（包含立直棒 -1000 成本），缩放 `net_pts / 25000.0`。

   * **半庄终局顺位分（Uma）**：在半庄结束时，将 `placement_bonus`（如天凤段位 PT `[+90, +45, 0, -135]` 或 `[+30, +10, -10, -30]` 归一化）作为终局奖励，跨局以 $\gamma_{\text{deal}} \approx 0.95$ 折现回传到每局最后一个决策点。

   * **彻底关闭 `shanten_weight`、`w_deal`、`w_survive`**：避免任何人工塑形破坏弃和、副露、流听之间的自然期望权衡。

2. **算法升级（重构 `train_hanchan.py`）**：

   * 将 MC 回报 `rt_chunk - values` 替换为 **GAE(**$\lambda=0.95, \gamma=0.99$**)**（在同一玩家连续决策步之间计算 TD 残差 $\delta_t = r_t + \gamma V(s_{t+1}) - V(s_t)$）。

   * **冻结主干的 Critic Warmup**：从方案 A 的凤桌 BC 权重起步时，先冻结主干与策略头训 20–50 轮 Critic（直到 explained variance > 0.3），再解冻策略头。

   * **自适应 KL 惩罚 + 对手池（League / Past Checkpoints）**：

     * 对手席位采用「50% 当前模型 + 30% 历史快照 + 20% 冻结的凤桌 BC / 外部强模型」，防止自对弈策略坍缩或互刷极端风格。

     * 保持到凤桌 BC 的 KL 锚定（`kl_coef = 0.05 -> 0.02`），防止策略忘记防守和流听。

   * **加大单次迭代批次**：利用 `mp_env.py` 多进程池，将每轮样本量从 16 半庄提升至 **64–128 半庄**（约 5–10 万步/iter），配合 minibatch shuffle 多轮 PPO 更新。

### 阶段验收指标

* 连续 50–100 iter 中，KL 散度稳定在 `0.02–0.15`，Critic explained variance > 0.35。

* 相对方案 A 凤桌 BC 底座，200+ 半庄盲测平均顺位提升（如从 2.50 降至 ≤ 2.35），且和牌率/放铳率/副露率不出现极端畸变。

### 风险与预案

* **风险**：纯 Python 多进程池吞吐仍受限（例如 16 核下约 10–30 局/秒），大规模 RL 收敛慢。

* **预案**：若超过 48 小时仍无稳定 Elo 提升，立即冻结在方案 A 最佳 BC 检查点，或转向方案 D 换高速引擎；切忌在低吞吐下强行调大 `lr` 或加回 `shanten_weight`。

## 方案 C（稳妥解耦兜底）：多专家模块化架构 + 强模型蒸馏

### 核心逻辑

如果受限于算力无法跑大规模凤桌全量 BC + 端到端 RL，可沿用仓库里已有的 `call_head.py`、`danger_model.py`、`distill_external.py` 资产，但**修正其设计缺陷**，实现低成本、可控的模块化强 AI。

### 具体实施步骤

1. **主干负责「门清/副露弃牌 + 立直 + 流听」**：

   * 在 Phase 0 修复后的环境与特征上，用中等规模凤桌数据（或 Suphx 蒸馏数据）训练 `DualStreamMahjongNet` 主策略。

2. **修复并升级独立副露头（重构 `call_head.py`）**：

   * 不再用 794 维扁平 MLP，改为共享主干表征或轻量交叉注意力头，输入显式包含「候选副露牌、叫牌后向听变化、是否有役（役牌/断幺/混一色潜力）、剩余巡目（支持终盘形式听牌副露）」。

   * 训练标签严格取自凤桌人类高手在「可叫牌局面」的真实决策（自然包含中盘速攻副露 + 终盘抢流听副露）。

3. **升级防守模块（重构 `danger_model.py`）**：

   * 去掉 `if melds != 0: continue` 限制，覆盖副露听牌对手。

   * 将**确定安全牌（现物）规则特征**直接硬编码为危险度 0.0，模型只预测非现物牌的放铳概率 $P(\text{deal-in} \mid t)$。

   * 推理融合采用期望值/攻防阈值切换（类似 `danger_model_agent.py`）：仅当「有对手立直或 2+ 副露高威胁」且「自身未听牌或低打点」时，按 `logit(t) - beta * P_danger(t)` 重排弃牌；听牌/终盘流听窗口动态降低 `beta`，避免过度弃和。

4. **外部强模型蒸馏（补齐低算力数据缺口）**：

   * 若凤桌原始数据下载/IO 受限，可用仓库已集成的 `SuphxFullAgent` 在修复后的 `MahjongEnv` 上跑 2000–5000 局生成软标签（logit distillation，KL 散度损失而非仅 hard top-1），同时蒸馏弃牌、副露、防守三项能力。

### 阶段验收指标

* 模块独立消融均须过门禁：

  * `+CallHead` 相比 `no_call`：平均得分与和牌率**双正收益**（彻底扭转此前 6.25% vs 10.00% 的负收益）。

  * `+DangerModule` 相比基线：放铳率显著下降（95% CI 不跨 0）且平均净点为正。

## 方案 D（长期上限路线）：替换底层为 C++/Rust 高速引擎 + 离线/在线 RL

### 核心逻辑

纯 Python 环境（`MahjongEnv` + `MahjongRepository/mahjong`）即便开多进程，单机吞吐上限也在几十局/秒量级，且自研规则细节（抢杠、包牌、九种九牌、四风连打、多重荣和、完整流局连庄）长期维护成本极高。若目标是做出真正可对抗天凤高段位/雀魂魂天级别的强 RL 模型，应直接站在成熟开源高速引擎之上。

### 具体实施步骤

1. **底层引擎选型（二选一）**：

   * **`mjx`（C++ 引擎 + Python 绑定）**：原生支持标准天凤规则、Gym 风格接口、高吞吐并行采样，自带标准观测编码器。

   * **`libriichi` / `mjai`（Rust 引擎，Mortal 同源）**：极致速度（单机轻松数百至数千局/秒）、规则 100% 对齐天凤凤桌，直接无缝对接 `houou_data` 的 MJAI 协议牌谱，离线训练与在线对战零格式转换损耗。

2. **保留本仓库核心资产**：

   * 保留 `DualStreamMahjongNet`（分花色卷积 + 事件流 Transformer 架构很干净）与评估体系（`arena_elo.py`、`eval_selfplay_gate.py`、`version_ladder.py`）。

3. **训练流水线**：

   * 第一阶段：全量凤桌 MJAI 牌谱监督学习（BC + 辅助危险张/向听/顺位预测）。

   * 第二阶段：在 Rust/C++ 引擎上跑大规模异步 Actor-Learner **PPO + GAE + IMPALA/V-trace**（千万局量级），以天凤段位 PT 为终局奖励，配合历史池与 KL 约束。

### 风险与预案

* **风险**：需要重新适配接口与数据管线，前期 1 周内不出新模型。

* **预案**：采用「双轨并行」——先用 3 天跑通 **Phase 0 + 方案 A** 拿到一个可对战、会副露/弃和/流听的基线模型，再决定是否切入方案 D 冲更高上限。

## 推荐执行顺序（行动清单）

1. **第 1 天**：完成 **Phase 0**（切通 `refengine` 算分 + 修副露/役牌/流局/连庄 Bug + 补 `obs2` 对手立直与现物平面 + 跑通全套回归测试）。
